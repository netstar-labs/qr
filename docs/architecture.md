# Architecture

`qr` is a QR Code encoder and decoder for Go that implements ISO/IEC 18004 with
**only the standard library**. This document maps the pipeline, names the file
that owns each stage, and states the trust boundary. It is a companion to
[VERIFICATION.md](../verify/VERIFICATION.md), which records how the parameter tables were
cross-checked.

## The two pipelines

```
ENCODE  (text ──▶ module matrix ──▶ PNG/ASCII)

  detectMode ─▶ chooseVersion ─▶ encodeSegment ─▶ buildCodewords ─▶ interleave ─▶ build ─▶ PNG
   encode.go      encode.go        encode.go        encode.go        qr.go     matrix.go  qr.go
                                     (bits)          (+RS ec)        (+mask)

DECODE  (matrix/image ──▶ text)

  sampleModules ─▶ readFormat ─▶ visitData ─▶ deinterleave ─▶ rsDecode ─▶ parseMessage
    decode.go       decode.go     matrix.go     decode.go     rsdecode.go   decode.go
    (image only)   (level,mask)  (unmask)      (+correct)                  (+validate)
```

Encode and decode are mirror images that meet at two shared definitions, on
purpose — a single source for each keeps the halves from drifting:

- **`visitData` (matrix.go)** — the zigzag traversal of the data region. The
  encoder places codeword bits with it; the decoder reads them back with it.
  One walk, so the placement and recovery orders are the same code, not two
  hand-matched loops.
- **`blockSpec.blockWords` (tables.go)** — the block partition. Interleaving and
  de-interleaving both derive their block sizes from it.
- **`dataBitCountN` (decode.go)** — the payload bit-length math, shared by the
  encoder's capacity check and the decoder's over-claim guard.

## Subsystems

### 1. Modes & segments — `encode.go`
`detectMode` picks the most compact of numeric / alphanumeric / byte.
`encodeSegment` writes the 4-bit mode indicator, the version-dependent
character-count indicator (ISO/IEC 18004 Table 3), and the packed payload into a
big-endian `bitBuffer`. `buildCodewords` then adds the terminator, pads to a
byte boundary, and fills to the version's data capacity with the alternating
`0xEC 0x11` pad bytes.

### 2. Galois field & Reed-Solomon — `galois.go`, `reedsolomon.go`, `rsdecode.go`
GF(256) is generated by the primitive polynomial `0x11D` with primitive element
2; `gfExp` is doubled so multiplication indexes without a modulo. The **encoder**
(`rsEncode`) divides the data by the degree-`ecLen` generator and keeps the
remainder. The **decoder** (`rsDecode`) is a full error-corrector: syndromes,
Berlekamp-Massey for the locator, a Chien search for positions, and Forney for
magnitudes — correcting up to `ecLen/2` errors per block, with a final syndrome
re-check so a mis-correction is reported, never returned as data.

### 3. Symbol assembly — `matrix.go`
`grid` carries the module colours and a parallel `reserved` mask marking
function-pattern and information cells. `placeFunctionPatterns` draws the three
finders (their border cells double as the light separators), the timing
patterns, the alignment patterns, and the fixed dark module. `placeData` streams
codeword bits through `visitData`. `build` tries all eight masks, scores each
with the four penalty rules (`mask.go`), and keeps the lowest — the mask, its
format info, and (for v≥7) version info are then written for real.

### 4. Format & version information — `format.go`
Both are BCH codes computed at runtime, not table constants — the format word is
BCH(15,5) with generator `0x537` XOR-masked with `0x5412`; the version word is
BCH(18,6) with generator `0x1F25`. Computing them shrinks the transcription
surface to two generator polynomials the tests anchor against known values.

### 5. Parameter tables — `tables.go`, `capacity.go`
The version-dependent constants: `ecTable` (block structure per version×level),
`totalCodewordsPerVersion`, `alignmentPositions`, `remainderBits`, and an
**independently transcribed** `dataCapacityCodewords`. The two capacity
representations are cross-checked against each other in tests and against Project
Nayuki and ZXing out of band (see VERIFICATION.md), so a same-total block swap
cannot pass silently.

### 6. Rendering & images — `qr.go`, `decode.go`
`QRCode.PNG` / `String` / `Matrix` render out; `DecodeMatrix` and `DecodePNG`
read back in. `DecodePNG` samples an upright, square-module image to a matrix —
it is a clean-image reader (renders, screenshots, flat scans), explicitly *not*
a perspective-correcting photo decoder.

## Trust boundary

The decoder treats its input as **hostile**. This matters because Reed-Solomon
correction is content-agnostic: *any* internally consistent codeword passes,
including ones a broken or malicious encoder produced. So every value the bit
stream yields is range-checked before use — numeric triples ≤ 999, alphanumeric
values < 45², and no segment may claim more characters than the remaining bits
can supply (`parseMessage`). Matrix geometry is validated before traversal, and
`DecodePNG` caps encoded size (32 MiB) and declared dimensions (32768²) via
`image.DecodeConfig` *before* allocating a pixel buffer, so a decompression bomb
is refused, not honoured. The invariants are held by four fuzz targets
(`fuzz_test.go`) at millions of executions: **decode never panics; it returns a
value or an error.**

The encoder trusts its caller: `Encode` selects the smallest fitting version and
returns an error only when content exceeds v40 capacity at the chosen level.

## Design constraints

- **Zero dependencies.** Standard library only — `image`, `image/{png,jpeg,gif}`,
  `bufio`, `bytes`, `errors`, `fmt`, `io`, `os`, `strconv`, `strings`. No
  `unsafe`, no reflection, no cgo.
- **Polynomials computed, not hard-coded.** Generators for RS, format, and
  version info are derived at runtime.
- **Kanji mode and ECI are omitted** by choice; byte mode emits raw bytes, which
  modern decoders read as UTF-8.
- **The example servers** (`example/http`, `example/unix`, `example/mcp`) are
  three separate, self-contained `main` programs — one per transport — that
  embed the library. None is part of it or adds a dependency to it.
